# AI Platform

Своя площадка для работы с ИИ через API. BYOK (bring your own key): ключи
хранятся только на устройстве, в IndexedDB, и уходят напрямую провайдеру —
посредников между пользователем и его ключом нет, включая нас самих. PWA:
ставится на macOS и iPhone из Safari, без App Store и без платы за аккаунт
разработчика. Бэкенда нет — браузер обращается к API провайдера напрямую.

Дизайн — язык Claude Code: тёплые нейтрали, единственный акцент клай
`#D97757`, моноширинный шрифт только на машинном слое (модели, токены,
код), обе темы (тёмная/светлая/системная), тач-таргеты и радиусы — из общих
CSS-токенов.

## Возможности

### Чаты и ветвление версий

Список чатов слева (постоянная колонка на широком экране, выезжающая панель
на телефоне), закрепление, папки, переименование из меню строки, поиск по
заголовкам и содержимому. Авто-заголовок берётся из первого вопроса.

Правка вопроса и регенерация ответа не удаляют историю — они создают
**версию-сиблинга**. Переключатель «‹ 1/2 ›» появляется у любого сообщения,
у которого больше одной версии, и переключает активную ветку чата. Модель
данных — два поля:

- `Message.parentId` — явный родитель сообщения в дереве (`null` — корень,
  `undefined` — legacy-сообщение из линейной цепочки старых чатов, которое
  нормализуется на лету: его эффективный родитель — предыдущее сообщение по
  `createdAt`);
- `Chat.activeLeafId` — id узла, на который сейчас смотрит чат.

Вся логика дерева — чистые функции в `src/lib/ai/tree.ts`, без единого
обращения к БД (принимают уже выбранный из Dexie массив сообщений одного
чата, отсортированный по `createdAt`). Инварианты, на которых стоит эта
модель:

1. Для чата, где у всех сообщений `parentId === undefined` (старые данные до
   этой функции), `buildPath` возвращает сообщения в исходном порядке — линейный
   чат — это ветка глубины N без единой записи миграции в БД.
2. runId-группа сравнения (см. ниже) — **атомарный узел** дерева: представитель
   группы — участник с минимальным `runIndex`, и члены группы никогда не
   расходятся по разным веткам (их эффективный родитель всегда равен
   эффективному родителю представителя).
3. `activeLeafId` после любой операции (правка, регенерация, удаление ветки)
   указывает на живое сообщение либо на `null`.
4. Переключатель версий (`siblingsOf`/`switchSibling`) считает **узлы**
   (представителей), а не отдельных членов runId-групп — иначе выбор
   победителя сравнения и переключение версий спорили бы за один UI-элемент.

Кнопка «Повторить» у ответа не стирает старый ответ: она открывает меню
(«та же модель» + все модели всех подключённых провайдеров) и создаёт
сиблинга с тем же `parentId`. Единый обработчик `ask({ leafId, model,
providerId })` в `ChatPage` обслуживает и обычную отправку, и правку, и
регенерацию — разница только в том, какой лист передаётся как родитель
нового ответа.

### Сравнение моделей

Один вопрос уходит одновременно в несколько моделей (кнопка «сравнить» в
композере), ответы печатаются параллельно и рисуются либо колонками (широкий
экран), либо вкладками с общей строкой цены (телефон). Ответы одного прогона
делят `runId`, `runIndex` — порядок колонки, `chosen` — победитель. В
контекст следующего вопроса уходит **только выбранный** ответ — остальные
остаются в переписке как история, но модель их больше не видит
(`toContext`, шаг 3 ниже).

Сравнение и ветвление версий сосуществуют благодаря пункту 2 инвариантов
выше: раз runId-группа — один узел дерева, для неё есть ровно один
переключатель версий (если у самой группы есть версии — например, вопрос
после неё был отредактирован) и ровно один выбор победителя (кнопка «крона»
внутри группы) — это два независимых UI-элемента, они не пересекаются.

### Artifacts — предпросмотр html/svg

Блок кода с языком `html` или `svg` получает кнопку «Предпросмотр»: код
рендерится в `<iframe sandbox="allow-scripts" srcDoc={...}>` — **без**
`allow-same-origin`. Это принципиально: без него iframe получает opaque
origin и не видит ни `IndexedDB` (где лежат ключи провайдеров), ни origin
приложения — это единственная граница безопасности BYOK-клиента, раз в
IndexedDB — реальные секреты пользователя. `svg` оборачивается в минимальный
html-документ с центрированием, иначе он не самостоятельный документ.
Предпросмотр открывается и в компактном виде (18rem высотой), и на весь
экран через оверлей-портал.

Демо-провайдер триггерит html-блок словом «html» в вопросе — иначе
предпросмотр непроверяем в smoke без живого API-провайдера.

### Сниппеты композера

`/` в пустом поле открывает меню быстрых вставок (стрелки — навигация,
Enter/Tab — вставка, Esc — закрыть). Три встроенных сниппета плюс свои,
редактируются в настройках. Композер — отдельный компонент со своим
состоянием черновика (текст, картинки, сниппет-меню): набор символа не
перерисовывает ленту сообщений выше. Наружу у композера — императивный
`handle { insertText, focus }` для приветственных чипов и правки по `↑`.

### Параметры чата, цены и расходы

Температура, максимум токенов и глубина рассуждения задаются в листе
системного промпта (он же — «параметры этого чата»), хранятся как
`number | null` (`null` — «не задано», поле не уходит в запрос вовсе, а не
отправляется каким-то принятым по умолчанию значением). В wire-запрос
попадают только когда значение действительно задано.

`reasoningEffort` (`'low' | 'medium' | 'high' | null`) уходит как
`reasoning_effort` и по умолчанию молчит: модели без поддержки на неизвестное
поле в теле отвечают 400, поэтому «не задано» — это отсутствие поля, а не
какое-то среднее значение. Признака «модель думающая» в данных нет вообще
(провайдеры отдают в `/models` только идентификаторы), поэтому подсказка под
регулятором опирается на эвристику `isReasoningModel()` по id — она влияет
только на текст подсказки, но не на то, что уходит провайдеру.

Цена модели — на самом провайдере: `Provider.models` — это `(string |
ProviderModel)[]`, где `ProviderModel = { id, priceIn?, priceOut? }` (₽ за 1M
токенов). Старые записи-строки (до этой функции) остаются в БД как есть и
читаются вечно — единственная точка нормализации `modelEntries()` в
`lib/ai/models.ts` превращает строку в `{id}`; и читатели (`ModelPicker`,
`CompareBar`, `CommandPalette`, `SettingsPage`, `ChatPage`, `RegenerateMenu`)
обязаны ходить только через неё. Стоимость запроса (`costRub`) смотрит цену
провайдера раньше встроенного реестра демо-моделей; в само сообщение
пишется **снимок** стоимости — прайс меняется со временем, а «сколько это
стоило» должно остаться фактом. Расходы за календарный месяц — в настройках,
с разбивкой по моделям.

### Поиск по содержимому

`src/lib/search.ts`, `searchAll(query, cap = 50)`: линейный проход по
`db.messages.filter(...)`, ограниченный `.limit(200)` — полнотекстовый
индекс был бы оверкиллом для локальной базы в тысячи сообщений, а лимит
достаточно рано обрывает проход. Один лучший (первый найденный) фрагмент
±40 символов на чат — выдача это «чат + фрагмент», а не лента сообщений;
совпадения по заголовку идут первыми. Используется и в сайдбаре, и в
командной палитре (⌘K), в обоих — debounce 200мс с `setState` только внутри
колбэка таймера (правило `react-hooks/set-state-in-effect` запрещает
синхронный `setState` прямо в теле эффекта).

### RU / EN

Один файл локализации `src/lib/i18n.ts`: словарь `ru` с namespaced-ключами
(`'chat.send'`, `'settings.theme.dark'`…), `en` типизирован как
`Record<TKey, string>` — компилятор ловит пропущенный перевод. Текущий язык
живёт в модульной переменной (не в React state/контексте) — `t()` нужна и
вне компонентов (`errorText` в `client.ts`, `demoReply`). `useT()` синхронный
через `useSyncExternalStore`. `LangApplier` в `App.tsx` читает
`settings.language` и зовёт `setLang`; `'system'` резолвится по
`navigator.language`. Дефолт до загрузки настроек из Dexie — `'ru'`.

Роли (personas) и встроенные сниппеты остаются русскими и не перегенерируются
при смене языка интерфейса — записи уже посеяны в БД пользователей, id
фиксированы, идемпотентность важнее локализации сида. Переводятся: весь UI,
тексты ошибок, демо-ответы (генерируются по языку в момент ответа — это код,
а не запись БД).

### Темы

Тёмная / светлая / системная, применяются мгновенно без перезагрузки;
`theme-color` синхронизирован с фоном каркаса — иначе в standalone-PWA на
iOS видна полоса чужого оттенка у краёв экрана. Выбор зеркалится в
`localStorage` (ключ `cc-theme`) и читается инлайн-скриптом в `index.html`
до первого кадра: сама тема живёт в IndexedDB, чей API асинхронный, и без
этого зеркала у светлого пользователя первый кадр всегда был тёмным.

### Агентские возможности

Кнопка-глобус в композере циклит три режима чата (хранятся в `Chat.toolMode`,
переживают перезагрузку): **выключено** → **поиск** → **исследование** →
снова выключено. В режимах «поиск»/«исследование» модель получает три
инструмента function calling:

- `web_search` — поиск по вебу через `s.jina.ai` (Jina AI), топ-5
  результатов с заголовком, ссылкой и коротким сниппетом;
- `read_page` — чтение страницы по URL через `r.jina.ai`, до 12 000 символов
  читаемого текста (дальше — обрезка с пометкой в самом тексте);
- `get_time` — текущие дата/время устройства с часовым поясом (без сети).

«Исследование» дополнительно подмешивает к системному промпту чата
русскоязычную инструкцию (`RESEARCH_SYSTEM` в `lib/ai/agentLoop.ts`,
wire-контент для модели, не UI-строка): краткий план, минимум три разных
поисковых запроса, чтение 2–3 источников, раздел «Источники» в конце ответа.
Каждый вызов инструмента — раунд агентского цикла (до 8 раундов в «поиске»,
до 12 в «исследовании»), после исчерпания лимита идёт финальный раунд без
инструментов — модель обязана ответить текстом.

Шаги цикла рисуются строками инструментов в стиле Claude Code — `▸ поиск:
запрос`, раскрываются кликом до полного результата шага. Во время стрима они
живут в React (`ChatPage`, не в Dexie); после ответа в БД пишется одно
финальное assistant-сообщение с полем `Message.toolTrace: ToolStep[]` —
свёрнутый заголовок «инструменты · N» в истории, раскрывается тем же кликом.
Результат каждого шага в `toolTrace` обрезан до 4000 символов (для
отображения) — полный результат (до 12 000) уходил модели только внутри
самого прогона и в истории не сохраняется.

Композер также принимает файлы — `.txt/.md/.csv/.json`, код (`.js/.py/.ts`…)
и `.pdf` (через `pdfjs-dist`, ленивый чанк `vendor-pdf`). В пузыре сообщения
виден только чип с именем файла и размером — извлечённый текст в ленте не
рендерится нигде, но уходит в запрос к модели вклеенным в контекст вопроса
(`<file name="…">…</file>` внутри `toContext`, см. «Архитектура» ниже).

**Честные ограничения:**

- **Браузер-only и BYOK.** Запросы к Jina AI уходят прямо из браузера
  пользователя — как и к любому другому провайдеру платформы, посредника нет.
- **Без ключа Jina — жёсткий rate limit** анонимных запросов. Ключ бесплатный
  (получить на [jina.ai](https://jina.ai)), хранится только в IndexedDB
  устройства и включается в те же вызовы `web_search`/`read_page`.
- **Чтение страницы** обрезается на 12 000 символах, **поиск** — топ-5
  результатов. Больше — не влезет в разумный бюджет одного раунда цикла.
- **Лимиты файлов:** текстовый файл — до 200 КБ (иначе отказ), PDF — до 25 МБ
  и до 50 страниц (дальше — обрезка с пометкой), суммарно на одно сообщение —
  до 60 000 символов текста файлов. Файл, не влезающий в остаток бюджета,
  подгоняется `fitFileText()`: берётся начало и конец документа по границам
  абзацев, а про выброшенную середину пишется прямо в тексте — его читает
  модель, и она должна знать, что видит документ не целиком. При нулевом
  остатке файл отклоняется с тостом.
- **PDF без текстового слоя** (скан) распознаётся по объёму текста на
  страницу: такие страницы рендерятся в JPEG 1600px и уходят картинками, их
  читает vision-модель. Локального OCR в проекте намеренно нет — `tesseract.js`
  это worker + wasm + языковые данные на десятки мегабайт в оффлайн-PWA ради
  качества хуже, чем у современных vision-моделей.
- **Не все модели поддерживают tools** (например, `deepseek-reasoner`).
  Платформа делает один повторный запрос без инструментов на первом раунде и
  показывает тост «модель без инструментов — отвечаю без поиска» — цикл
  продолжается обычным ответом.
- **Инструментные сообщения не попадают в контекст следующих вопросов** — в
  `toContext` уходит только финальный текст ответа, шаги вызовов инструментов
  модель на следующем вопросе уже не видит.

## Дизайн-система

Язык — Claude Code: тёплые нейтрали oklch, один акцент-клай, моно только на
машинном слое. Токены живут в `src/index.css` двумя семействами: `--app-*`
(цвета, меняются по теме, мост в Tailwind через `@theme inline`) и `--cc-*`
(метрика, время, поверхности). Спецификация с артбордами — в
`docs/design-canvas/` (файлы `.dc.html` + `canvas.json`, пересобираются
хелпером Claude Design).

Что задаёт систему:

- **Поверхности** — монотонная лестница `bg → surface → surface-2 →
  elevated`. Каждая следующая светлее предыдущей; до правки 22.08.2026
  `elevated` был темнее `surface-2`, и поповеры читались как провал.
- **Высота** — четыре ступени `--cc-elev-rest/raised/overlay/modal`. В
  тёмной теме каждая несёт верхний inset-блик: чёрная тень по почти-чёрному
  фону края не создаёт, поверхность отделяет именно светлая линия сверху.
- **Состояния** — заливками, не прозрачностью: `--cc-fill-hover/press/
  selected/disabled` и класс `.cc-hit` на интерактивной зоне. Глобальное
  `button:hover { opacity: .85 }` осталось запасным для неразмеченных
  кнопок — миграция сырых `<button>` идёт постепенно.
- **Текст на акценте** — только через `--cc-on-accent`. В тёмной теме акцент
  светлый (L 0.672), белый по нему даёт ~2.4:1 и норму не проходит.
- **Движение** — `--cc-dur-fast/snap/base` (60/120/200 мс) и две кривые
  `--cc-ease-out` / `--cc-ease-snap`. Уход всегда быстрее прихода (0.7 от
  входа). `prefers-reduced-motion` гасит и мигающую каретку, и нажатия.
- **Слои** — шкала `--cc-z-sticky/popover/scrim/sheet/full/toast` вместо
  россыпи чисел по файлам.
- **Иконки** — свой набор из 45 глифов (`components/ui/glyphs.tsx`) с
  оптической компенсацией штриха: толщина считается от размера и держит
  экранную линию в коридоре 1.3–1.6px. Без компенсации 1.75 в поле 24 даёт
  0.80px на значке 11px и 1.90px на 26px.
- **Тач-цели** — `.cc-tap` растит зону касания до `--cc-touch` только на
  `pointer: coarse`; там, где кнопку нельзя увеличить визуально, работает
  невидимый ореол `.cc-tap-halo`.

## Архитектура

```
src/
  db/{types,db}.ts         — схема Dexie и типы записей
  lib/repo.ts               — общие хелперы записи (id, штампы времени, мягкое удаление)
  lib/{backup,images,search,i18n}.ts
  lib/ai/{client,chatRepo,personaRepo,snippetRepo,models,tree}.ts
  features/chat/            — ChatPage и всё вокруг ленты и композера
  features/settings/        — SettingsPage, формы провайдера и сниппета
  components/ui/            — Toast, Sheet, Button — переиспользуемые примитивы
```

### Слой данных (Dexie)

Каждая запись наследует `BaseEntity` (`id` uuid, `createdAt`, `updatedAt`,
`deletedAt` — мягкое удаление: именно оно позволяет синхронизации доносить
удаления до второго устройства, физический delete в коде запрещён).

Схема — `SCHEMA_VERSION = 5`:

```
v1: chats, messages, providers, settings
v2: + personas                (библиотека ролей)
v3: + snippets                (библиотека сниппетов композера)
v4: + syncConfig              (конфиг синхронизации, одна строка)
v5: индекс createdAt у messages (диапазон вместо полного скана в статистике)
```

Правило проекта, которое держит эту таблицу короткой: **новая таблица — новая
версия Dexie, которая объявляет только её; определения прежних таблиц
Dexie наследует дословно из предыдущей версии.** Неиндексируемые поля новой
версии не требуют — `parentId`, `activeLeafId`, `temperature`, `maxTokens`,
цены моделей внутри `Provider.models` — всё это обычные поля объектов,
которые Dexie хранит как есть без объявления в `stores()`. Это осознанный
компромисс ради прода с данными: приложение уже установлено у пользователей,
и минимальная миграция — минимальный риск потери данных. Обратная
совместимость всюду — **чтением, а не миграцией**: старые записи-строки в
`Provider.models`, сообщения без `parentId` (`undefined`) — читаются вечно,
включая импорт старых JSON-снапшотов.

### Алгоритм `toContext` (что реально уходит в модель)

`src/lib/ai/chatRepo.ts`, вызывается перед каждым запросом:

1. `path = buildPath(messages, activeLeafId)` — путь от корня до активного
   листа чата; runId-группы разворачиваются на месте представителя всеми
   членами по `runIndex`.
2. Фильтр: `status === 'done'` и есть непустой `content` либо `images`
   (пустой `content` — это ошибка или отмена, провайдер отверг бы такое
   400-й ошибкой).
3. Из каждой runId-группы в контекст идёт **только победитель** — `chosen`,
   либо участник с минимальным `runIndex`, если выбор ещё не сделан.
4. Хвост из `historyLimit` последних сообщений (0 и меньше — без среза) —
   прямой контроль расхода: без него длинный диалог оплачивается целиком на
   каждом следующем вопросе.
5. Превращение в `{ role, content, images }` — wire-формат для
   `streamChat`/`requestChat`.

### Провайдеры

Все поддерживаемые API — OpenAI-совместимые (`POST /chat/completions`),
поэтому один адаптер закрывает и российские агрегаторы, и зарубежные
сервисы, и локальный сервер — различаются только `baseUrl` и ключ. Anthropic
и Google подключаются через свои слои OpenAI-совместимости; собственный
формат Messages отдельным адаптером пока не нужен.

Пресеты живут в `src/lib/ai/presets.ts` и разбиты на три группы по тому, что
реально важно из России: агрегаторы (рубли, без VPN), прямые API, которые
отвечают из России, и западные вендоры, где нужен VPN или прокси.

**Моделей в пресетах нет намеренно.** Первая версия пресета DeepSeek приехала
с зашитыми `deepseek-chat` / `deepseek-reasoner` и устарела в тот же день —
у провайдера сменилась линейка на `deepseek-v4-*`. Пресет заполняет только
адрес; список моделей приезжает кнопкой «Подтянуть список» и подтягивается
автоматически, если ключ уже введён. Живой ответ провайдера всегда точнее
хардкода.

#### Anthropic — что проверено и как это устроено

Claude подключается по адресу `https://api.anthropic.com/v1` через слой
OpenAI-совместимости. Проверено вживую зондом из браузера (ключ заведомо
неверный, важен сам транспорт):

- **Без заголовка `anthropic-dangerous-direct-browser-access` браузер не
  отправляет запрос вообще** — предполётный OPTIONS возвращает 400, `fetch`
  падает с `Failed to fetch`. С заголовком предполёт возвращает 200, а сам
  запрос — читаемый JSON. Поэтому заголовок не «на всякий случай», а условие
  работоспособности.
- `access-control-allow-origin: *`, в `allow-headers` перечислены ровно
  `authorization, content-type, anthropic-version,
  anthropic-dangerous-direct-browser-access`.

Из документации совместимости: `stream`, `stream_options`, `tools`,
`image_url` поддержаны полностью; `temperature` выше 1 обрезается до 1;
`usage.*_tokens_details` всегда пустые (значит счётчик мыслей и кеша у Claude
будет нулевым); **`reasoning_effort` игнорируется**.

Из-за последнего глубина рассуждения для Anthropic отправляется иначе, и
вариант зависит от поколения модели (`providerTuning()` в `presets.ts`):

| Поколение | Что уходит |
|---|---|
| 4.6 и новее (включая Claude 5) | `thinking: {type: 'adaptive'}` + `output_config: {effort}` |
| 4.5 и старее | `thinking: {type: 'enabled', budget_tokens}`, минимум 1024 и строго меньше `max_tokens` |

Поколение определяется эвристикой по идентификатору, а страхует её фолбэк в
`client.ts`: если провайдер ответил 400 на запрос с этими полями, запрос
повторяется без них и пользователь видит тост. Ответ важнее регулятора —
чат не должен падать из-за настройки.

Текст рассуждения слой совместимости не возвращает: блок «рассуждение» у
ответов Claude будет пустым, и об этом прямо написано в подсказке под
регулятором.

Заголовки запроса собирает `providerHeaders()` там же. Обычным провайдерам
уходит только `Authorization: Bearer` — лишние поля часть агрегаторов
отвергает на предполёте. Anthropic получает дополнительно `anthropic-version`
и `anthropic-dangerous-direct-browser-access`: без второго браузерный доступ
к их API закрыт наглухо, предполётный CORS-запрос не проходит.

**Известное ограничение:** браузерный запрос к зарубежному API из России
упирается и в CORS, и в геоблокировку по региону (403). Российские
агрегаторы (Polza.ai, VseGPT, BotHub) этой проблемы не имеют — они и стоят
первыми в пресетах формы.

## Синхронизация мак↔айфон и серверный поиск

Опциональный слой поверх локальной базы: воркер Cloudflare (`server/`,
деплой — workflow «Деплой воркера») хранит в D1 только шифротекст.
Идентичность без аккаунтов: из секретной фразы на устройстве выводятся
(PBKDF2 → HKDF) адрес пространства, токен и ключ AES-GCM; одинаковая фраза
на двух устройствах объединяет их данные, сама фраза не хранится нигде.
Клиентский цикл — `src/lib/sync/engine.ts`: полуоткрытое окно push,
постраничный pull с курсором по паре `(updatedAt, id)`, LWW по `updatedAt`.

Тот же воркер отдаёт `/search` — прокси к google-выдаче (Serper) для
инструмента `web_search`; при недоступном сервере поиск молча откатывается
на Jina. Пошаговая настройка — `docs/SYNC-SETUP.md`.

## Безопасность

- **Ключи** провайдеров лежат в IndexedDB устройства открытым текстом и
  уходят только напрямую провайдеру — платформа BYOK, посредников (включая
  наш собственный сервер — его нет) между пользователем и ключом нет.
- **iframe предпросмотра** — `sandbox="allow-scripts"` без
  `allow-same-origin`: содержимое получает opaque origin, не видит ни
  `IndexedDB` с ключами, ни origin приложения. Добавлять
  `allow-same-origin` нельзя ни при каких доработках — это стирает границу.
- **Markdown** ответов — только через `marked.parse` + `DOMPurify.sanitize`
  (форма, `input`, `iframe`, `script`, инлайновые обработчики — под запретом
  в самой разметке ответа; iframe предпросмотра — единственный осознанный, с
  явной песочницей выше). Ссылки — принудительно `target="_blank"
  rel="noopener noreferrer"`.
- Экспорт снапшота предупреждает, что в файле есть API-ключи, до скачивания.

### Мемоизация ленты чата

`UserBubble`, `AssistantBlock`, `CompareGroup`, `VersionNav` обёрнуты в
`React.memo`. Чтобы это вообще что-то давало, все колбэки, уходящие в них
из `ChatPage`, — **одна стабильная ссылка на весь список**, а не
инлайн-фабрика внутри `.map()`: `copyText`, `switchLeaf`, `handleSubmitEdit`,
`handleRegenerate`, `handleDeleteBranch` оборачивают `useCallback`, и в JSX
передаются как есть (`onCopy={copyText}`, `onRegenerate={handleRegenerate}`
и т.д.) — сам компонент прикладывает к колбэку свой `message`/`id` при
вызове (`onClick={() => onCopy(message.content)}` уже **внутри**
`UserBubble`, а не в `ChatPage`). Дополнительно `ask`/`askCompare` больше не
зависят от целого объекта `settings` (любое его поле — новая ссылка целиком,
включая тему и язык, которые к отправке отношения не имеют) — только от
примитивов `historyLimit` и `hasSettings`, которые не меняются при смене
темы или языка.

Эффект: набор текста в композере не задевает `ChatPage` вовсе (черновик —
состояние компонента `Composer`, из T4), а стрим ответа перерисовывает
только сам `Streaming`-блок — уже отрисованные `UserBubble`/`AssistantBlock`
ленты остаются нетронутыми (проверяется профайлером React DevTools: во время
стрима подсвечивается перерисовкой один последний блок).

### Побочная находка: гонка `chats`/`messages` при быстром Esc

В процессе профилирования всплыл реальный баг, не связанный напрямую с
мемоизацией: `addMessage` писал в `db.chats` **дважды** подряд —
`lastMessageAt` внутри себя и `activeLeafId` отдельным `patchChat()` сразу
после. Между этими двумя записями `useLiveQuery(chats)` иногда успевал
отрисовать чат с уже новым `lastMessageAt`, но ещё старым `activeLeafId` —
и наоборот, теряя кадр с полностью consistent-состоянием на медленной
машине или при плотном потоке событий (обрыв генерации по `Esc` сразу после
отправки — именно такой сценарий воспроизводил пропажу последнего ответа из
ленты). Исправлено объединением обеих записей в один `db.chats.update()` —
`addMessage` принимает опцию `asActiveLeaf`, и `activeLeafId` уходит в ТОЙ ЖЕ
транзакции, что и `lastMessageAt`.

## Деплой

Actions**. Адрес — `https://xabos161rus-pixel.github.io/ai-platform/`.
